# 审阅分级与合并门禁（通用口径）

> 2026-11-19 主人定。适用于本仓库，以及经 Hub 调度完成的所有目标项目的独立审阅。
> 这是分级口径的唯一来源：`AGENTS.md`、全局 `~/AGENTS.md`、调度规则里的审阅提示词都按本文同步，改口径先改这里。

## 为什么这样定

对 #64、#83、#82 三个 PR 的 48 条 P0–P2 复盘发现：门禁偏紧的主因不是复审范围，而是“不会真实发生的问题也拦合并”。
#82 的 9 条 P0 全部依赖“worker 主动作恶篡改共享 Git 配置”这一威胁模型，而 worker 与控制器本就同一系统用户，拖成 8 轮返工；
每多修一条不会发生的问题，又会引入新的返工问题（首轮后的新问题约 85% 由返工引入）。

## 拦截条件：三条同时满足才算 P0–P2

1. **会真实发生**：按正常使用判断，默认把 worker、作者 Agent 视为合作方而非攻击者。
   以下四类例外按对抗场景审（恶意输入、越权、伪造都要考虑）：
   - 处理外部不可信输入（公网请求、第三方回调、用户上传内容）；
   - 多租户（跨租户隔离、owner 校验）；
   - 真实资金（支付、记账、持仓、计费扣款）；
   - 个人隐私或凭据（个人数据、密钥、令牌）。
2. **是这次 PR 造成的**：这次改动引入的，或这次改动让原本不可达的问题变得可触发。
   PR 未改动的旧代码问题不算本 PR 的拦截项。
3. **后果达到该级标准**：

| 级别 | 后果标准 |
| --- | --- |
| P0 | 真实丢钱、丢数据或数据写错、泄露隐私或凭据 |
| P1 | 主流程坏掉、结果算错、事务半途留下不一致状态 |
| P2 | 常见使用场景下的行为回归或明显错误 |
| P3 | 其余一切：罕见边界、只在人为构造/对抗场景出现（四类例外外）、旧代码问题、测试卫生、可读性与优雅性建议 |

补充：

- 测试会必然变红（例如写死日期的定时炸弹、必现的 CI 竞争）按 P1 拦截：CI 红等于主流程坏掉。
- 拿不准是否“会真实发生”时，写出触发条件，按能举出的最现实场景定级；举不出现实场景的定为 P3。

## 不拦截的问题怎么处理

- P3 不阻断合并，但必须登记：写进 PR 描述的“已知后续”小节（问题、触发条件、建议修法），需要时由调度方另开任务。
- 复审只核对上一轮 P0–P2 是否修好，以及修复本身是否引入新的 P0–P2；新发现的问题同样按本文三条判定。
- 返工上限、squash 合并、不直推主干等流程规则不变（见 `AGENTS.md` 第 8 节）。
