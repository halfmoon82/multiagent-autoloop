# 设计稿门 PRD：前置确认、基线遵守与无门禁自愈

- 状态：已确认（2026-11-23）
- 独立审阅：设计稿门防阻塞独立审阅，P0=0；P1/P2 已纳入本版

## 背景与问题

现有机制曾提供设计基线和证据（PR #82），随后被改成只报不拦（PR #109）。PR #248 的批准文件和快照也不能证明真实 run 已接入设计设施。NoMoTo 的实际执行因此出现：功能测试通过，但实现与高保真设计不一致；同时，简单恢复硬门又可能在 DAG 运行中制造 blocked/gated 和中途返回。

## 当前实现基线（2026-11-23）

#252（`7ea6ea54a2`）已合并：内容寻址冻结与恢复、证据失效自动补验、checks/knownDeviations 未通过时正常返工且不合并，以及部分契约文档。这些能力不在本 DAG 重复建设。剩余差距为：UI 双向覆盖与事务预检、批准样例/备用采集能力、显式可查询的 codeReviewAccepted 与 designConformance 两项结论、剩余故障注入与集成证明。#252 的 accepted + 内部 designDeviation 判定尚不等于两项独立可查询结论。

## 用户与场景

- 设计会话：涉及交互界面时必须形成完整、可验收、经本人确认的设计基线。
- 调度会话：只接收已确认基线的 UI 开发计划，并保证每个 UI 范围都有节点负责。
- Worker/reviewer：按同一基线实现与独立验收，不能用字段或测试绿代替视觉与交互一致。
- 本人：只在设计阶段确认设计语义，不在开发运行中处理工程故障或工程选项。

## 输入

- 页面/状态/交互/视口/视觉参考及批准记录。
- 页面/状态/交互到 DAG 节点的双向覆盖矩阵。
- 冻结设计包、精确实现 commit、独立渲染证据。

## 输出

- 创建前完整预检和原子 run 创建。
- 控制器拥有、内容寻址、可恢复的设计冻结存储。
- 运行中无设计专用 blocked/gated 的证据恢复与正常返工。
- 分离的代码审阅结论与设计符合性结论。

## 成功标准

1. UI 设计未形成已确认基线时不创建 DAG，但不产生运行中门禁。
2. 活跃 run 不读取新稿、不要求再次批准，只使用创建时验证可恢复的冻结副本。
3. 基线、证据、截图、verifier、依赖、浏览器或 worker 失败均由调度通过恢复、重建、换打法或无模型脚本继续。
4. 设计偏差必须进入正常 review→rework，不得宣称设计验收通过，不静默合并为“已对齐”。
5. 纯后端路径不加载设计设施。
6. NoMoTo 同类“会话页无人负责视觉、真实 run designBaseline/designEvidence 为 null”在创建前即可发现。

## 失败行为

- 预检失败：留在设计或环境修复阶段，不留下可派发的半成品 run。
- 运行中设施失败：进入 evidence-recovery，不计 worker 实现失败。
- 运行中实现偏差：进入正常返工，不进入设计专用 blocked/gated。
- 全局所有替代方式穷尽仍失败：沿用项目既有升级规则，不由设计稿门新增升级路径。

## 非目标

- 不修改 NoMoTo 业务页面。
- 不部署、不重启真实控制台、不修改真实调度规则。
- 不要求机械像素门或把主观视觉偏好自动化成合并门。
- 不让 worker 修改基线、选择产品语义或处理部署授权。

```bash
npm run test:browser
```
