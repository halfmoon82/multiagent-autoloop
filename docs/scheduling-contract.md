# 调度会话与事件链契约

## 定义

**调度会话**是控制面中的协调上下文：选择任务和模型、创建事件、观察状态、诊断失败、组织独立审阅并处理交付事务。

**执行任务**是目标项目中的具体实现。它在目标项目的隔离工作区运行，拥有自己的需求、代码、测试、Git 提交和发布授权。

调度会话位于本项目不等于目标任务代码属于本项目。

## 调度方职责

1. 读取规则、轮次、卡片、`why` 和相关日志，先判断失败原因。
2. 按任务复杂度、失败成本和审阅风险选择最具性价比的平台/模型。
3. 可自愈的本地脚本、配置、状态和规则问题直接修复，做最小验证后恢复或重触发。
4. 组织开发、独立审阅、返工和合并；保持目标项目工作区与 Git 边界。审阅分级与合并门禁统一按 [review-severity.md](review-severity.md)，派发 reviewer 时写入其拦截三条件与四类例外（含“只防外部一方”）。
5. 对无模型可发现的异常使用定时扫描，命中后再唤醒调度 Agent；相同异常在冷却期内不重复唤醒。
6. 只有《升级给用户的最小门禁》列出的事项才请用户决策，其余一律由调度方处理并担责。

“待调度处理”默认由调度方推进，不能把所有开放卡片直接转嫁给用户。

## 升级给用户的最小门禁（2026-11-14 收紧）

用户是产品经理，只决策产品类问题（另加两类必经升级：用户独有凭据、穷举失败）；工程实现一律由调度方自行决定、执行并担责。
生成「待我处理」卡片仅限以下六类，卡片文本必须说明业务含义与后果，不得罗列工程选项：

1. **产品功能**：改变产品真正功能、用户可见行为、利益或责任边界的选择。
2. **个人隐私**：个人数据的收集、使用、保留或对外提供。
3. **财务**：会产生真实花费、采购、定价或预算超支的事。
4. **对外影响**：对他人可能造成误导或影响的事件（公开发布、对外消息、第三方可见变更）。
5. **只有用户掌握的 key、凭据、账号或授权**：只说明缺什么、给出恢复路径，不让用户选择工程方案。
6. **穷举失败**：按重试纪律穷尽替代方式（换 Agent、换模型、拆小任务、改无模型脚本）仍失败，必须改变打法的任务——挂起并向用户报告分歧点。

**禁止升级**（调度方必须自行处理，不得包装成选项卡片）：工程实现选型与方案对比、
重试与自愈、模型选择、worktree 与分支、依赖与环境修复、脚本与状态修复、
规则启停、审阅返工。用户已多次决策但问题仍未解决的工程事项，调度方必须自己动手
落地或换打法，禁止反复生成同类卡片催人。

### 初始化时必须继承的发卡纪律（2026-11-17）

任何项目初始化、调度规则模板和调度会话提示词都必须完整继承以下四项，不得只登记在单个项目，也不得用「同上」等依赖另一规则副本的省略写法；每条模板可独立阅读，术语统一使用「本人/用户」：

【发卡纪律·初始化原则】① ask 仅限六类：产品功能、个人隐私、财务、对外影响、只有本人掌握的凭据与授权、换打法满 3 次仍失败。② 写权限、通道与配置、模型与额度、返工与复审安排、worktree/分支、环境依赖、脚本与状态、规则启停等工程问题一律自行处理或换打法（改派可写通道、无模型脚本、notice 挂起留痕），不得 ask，不得让本人代跑工程命令。③ 同一阻塞已有 open 卡不得重发 ask；同问题发过卡未解决必须换打法，禁止再发同类卡。④ 发现「任务要求写文件但本通道只读」的契约错配：汇报首行写「契约错配：<规则名>」，由调度方改派可写通道，不向本人发卡。

【审阅分级·初始化原则】拦截三条件同时满足才算 P0–P2：①会真实发生——worker、作者 Agent、同一系统用户一律按合作方，不按攻击者；②是本 PR 引入或让其变得可触发的，未改动的旧代码问题不算；③后果够级：P0 真实丢钱/丢数据/持久化数据写错/泄露隐私或凭据，P1 主流程坏或计算/展示结果错或事务留下不一致，P2 常见场景下的行为回归或明显错误。四类例外按对抗场景审：本 PR 改到处理外部不可信输入、多租户、真实资金、个人隐私/凭据的代码路径时，考虑恶意输入、越权和伪造，但只防外部一方。其余一律 P3 不拦合并，但须登记在 PR 描述的“已知后续”。必然变红的测试按 P1 拦；必须有的回归测试缺失按所修缺陷的级别定级；重试、并发、进程中途退出算正常使用；拿不准时按最现实场景定级，举不出现实场景的定 P3。复审以核对上一轮修复为主，但满足三条件的问题不论哪一轮发现都拦。同一 PR 同时只许一方审阅和合并：审阅前先在 PR 上占位，他人已占位就停止，合并只能由占位者按审过的提交执行。完整说明见控制面仓库 multiagent-autoloop 的 docs/review-severity.md。

初始化新项目时，项目的 AGENTS.md、调度契约、规则模板与调度提示词都要独立携带这四项；验收时用一个新项目夹具断言模板含六类门禁、工程不 ask、open 卡去重和只读契约错配改派。

初始化新项目时，审阅规则模板与项目 AGENTS.md 同样独立携带上面的【审阅分级·初始化原则】，不写成“见某文件”的引用。

### 卡片退回调度与语言质量门（2026-11-17）

- 所有开放卡片提供独立「退回调度处理」动作，不改原 options 顺序与答案。
- 退回是事务：先创建调度事件（含卡片编号、项目、标题、正文、选项与最小上下文），Hub 接受后才结案原卡（reason：已退回调度处理）；事件失败原卡保持开放，重试复用同一幂等键，不重复产生 Hub run。
- 调度仍需人类时创建 `revision+1` 新卡并链接原卡、补齐证据与产品语言，不原样重发同一卡；同一链往返有冷却与循环检测。
- 卡片语言质量门检查决策问题标题、产品语言背景、待决原因与不决定后果、每个选项的收益与代价、推荐理由；缺项、裸选项、技术黑话产生可测试的质量错误，不合格卡退回调度方重写，不静默删除、不自动作答。

## 待我处理卡片陈述规则（2026-11-15 主人定）

用户是产品经理，靠卡片做决策。卡片写不好等于把工程问题重新推回给用户，违反本节的
卡片应由生成方重写后再发，控制台只负责如实呈现。

1. **背景用产品经理能听懂的话**：发生了什么（从用户/业务视角说）、现在需要决定什么、
   不做决定的后果是什么。**禁止出现函数名、内部文件名、目录路径、堆栈、接口名、
   技术黑话**；绕不开的技术概念，用一句业务后果解释（例如"这一步会让服务在半夜重启"
   而不是"修改 supervisor 的 restart policy"）。
2. **每个选项必须注明收益和代价**：各一句话，代价要包含金钱、时间或风险中至少一项；
   只给选项不给利弊的卡片视为不合格，不得发出。
3. **有推荐项时必须说明推荐理由**（为什么是它而不是其它选项），推荐理由同样用产品语言。
4. **标题是一句完整的决策问题**（例如"责任闭环是继续补齐剩余四项，还是拆到后续节点？"），
   不是技术短语或文件名。
5. 卡片归属项目优先使用卡片上报的项目字段，否则归属创建它的调度规则的工作目录，
   控制台按此分组呈现；生成方不得伪造项目字段。

## 通道-写意图契约校验（2026-11-16 机制事故加固）

控制台保存规则时校验契约错配：提示词出现明确写意图信号（写动词紧邻 state.nodes、写动词紧邻
serial.json 台账、落地补丁、直接修复、修改 rules.json/补丁——「读取/只读提述」不计）、
落地补丁、直接修复、修改 rules.json/补丁）而目标 Agent 为只读通道时拒绝保存，提示改选可写
Agent 或改写成只读提示词。否定豁免只认紧邻动词的禁止（「不要修改 rules.json」类），跨逗号/桥接词的否定（「别犹豫，把授权写入台账」）仍判写意图——这是启发式边界。编辑存量规则时整表校验（含未改动的提示词）：带写意图词的旧规则须先修复错配或改走 detour 换 Agent，此为本校验的刻意约束。背景：2026-11-14/15
「调度自愈处理」「执行波门禁处理」提示词要求写文件却绑只读 codex 通道，运行期死锁并连续 13 张
工程卡打扰店主；事故后运行时改派 codex-full/workbuddy 可写通道，本条为工具层防复发。

## 串行链收口（2026-11-17）

无模型收口巡检（控制台服务端，5 分钟一轮，`AUTOLOOP_CLOSEOUT=0` 可关）：

1. `*-serial.json` 全部节点 `done` 且文件 30 分钟无写入，判定收口；
2. 暂停该链**独占**的 cron 规则（中台 `pause`，不动 rules.json，`agent-autoloop resume <规则>` 可恢复）；被其他在途链共享的 cron 规则绝不暂停；事件规则不处理（无事件源自然不触发）；
3. 链文件原位归档为 `<文件名>.done-<yyyymmdd>`，进度面板随之撤下；
4. 动作记入 `<运行目录>/closeouts.jsonl`，控制台 `GET /api/closeouts` 可查；
5. 中台暂停失败则不归档，下轮重试；链若复活（同名文件重建），不自动 resume，由调度方按审计记录里的命令恢复。

## 节点进度上报（2026-11-15）

串行推进编排器维护 `<AGENT_AUTOLOOP_HOME>/<链名>-serial.json`（既有约定），控制台总览
"项目任务进度"面板据此渲染任务条与整体百分比。编排器必须：

1. 顶层写 `project`（被调度项目绝对路径），供控制台归组；
2. 按执行序维护 `plan: ["节点id", ...]`；缺省时控制台按写入顺序展示，可能不准；
3. 节点状态沿用既有词表（done / pending / dev_dispatched / external_in_progress / blocked 等），
   当前节点尽量写 `part`（如"审阅返工"）与 `percent`（0–100 整数），不写时控制台按状态默认值显示；
4. 每个节点写 `title`（业务标题，说明这个节点交付什么功能或服务）与 `summary`
   （产品语言的一句话进展，控制台节点浮层全文展示）。

## 模型派发规则

- 调度会话必须根据任务复杂度、失败成本和审阅风险选择最具性价比的平台/模型。
- 独立审阅和资金、数据、安全相关任务优先保证可靠性，不得为省钱降低资金、数据或安全审阅质量。
- 控制台只展示实际发现的模型；费用只能使用 Hub 上报，不能按模型名称猜测。
- 频限绕行（2026-11-15 主人定）：会话因模型频限被拦下时，调度方可以派发其他模型、甚至迁移宿主平台继续推进；这不视为违反派发规则，也不需要升级用户。
- 绕行必须留痕并核实恢复：记录被拦模型/宿主、拦下时间与频限证据（错误码或提示原文）、替代方案；对被拦模型按冷却节奏做最小成本核实，不得靠反复全量派发试探恢复。
- 核实恢复后回归正常派发规则：恢复原模型/宿主为默认派发，绕行模型不沉淀为新的派发偏好；长期未恢复则维持绕行并保留记录，核实通过时自动回归。
- DAG 节点自动分档（2026-11-19 主人定，成本优先）：控制器按节点给出 `light / standard / heavy`（`src/dag-tier.mjs`）。节点可写 `complexity` 显式指定，否则按改动文件数推断（≤2 light、3–6 standard、更多 heavy）；审阅至少 standard；节点 `risk` 含 funds/data/security 或改动命中支付、账务、认证、凭据、迁移等敏感路径时，开发至少 standard、审阅 heavy。同一节点满 3 次失败换打法时默认升一档，不直接上最贵模型。
- 平台与模型（2026-11-19 主人定，管理后台维护）：控制台「管理后台 › 平台与模型」是人维护这套配置的唯一入口（`src/platform-models.mjs`）。
  - 平台 = 宿主程序（Codex、Claude Code、每个 ACP 程序如 WorkBuddy），不是执行者（2026-11-19 主人定）：同一程序上的多个执行者（如 `codex`、`codex-full`、项目专用的 `liuxue-heal`）合并为一个平台；脚本与通知渠道类（command、feishu、webhook 等）不算平台。新程序登记后自动出现。每个平台选一个「模板执行者」复制出分档执行者：可写优先，其次工作分配在用、与程序同名、被规则引用更多；已保存的平台 id 保持稳定。每个平台各配便宜档/中档/高档三个模型，未配齐的新平台只用它自己的默认模型、不进入工作分配。
  - 工作分配：开发、审阅、调度会话各设主/备平台（即 `detour-policy.json` 的 `defaults`，频限绕行共用），频限时切备用平台的**同一档**；调度、设计、普通会话各选一个固定档位。设计/普通会话目前只能用 Codex 类平台：WorkBuddy 的 ACP 会话模式没有只读/工作区写沙箱，会话护栏无法等价核验，暂不接入。
  - 保存（状态锁内、先中台校验、先备份 `rules.json.bak-<时间>-platform-models`）：生成 `<平台>-tier-<档>` 执行者、为已发现 Git 项目的 DAG 规则生成 `·<档>` 分档规则（审阅不生成便宜档）、调度会话规则指向对应档位执行者；原规则保留作兜底。有进行中的频限绕行涉及分档或调度会话规则时拒绝保存。关闭开关即清掉生成物并让调度会话规则回到主平台。
  - DAG 派发事件类型只在开关开启**且** rules.json 确有规则接收 `dag.<项目>.<角色>.<档>` 时才带档位后缀，否则回落 `dag.<项目>.<角色>`；事件 detail 始终记录 `tier`。

## 事件链不变量

- 事件分支按真实依赖连接。可并行的部署、开发和审阅不得互相阻塞。
- 特别地，NAS 或其他部署结果不得成为检查远端代码、启动开发或审阅的前置条件。
- 事件 `subject` 使用无空格的稳定 ASCII 标识，例如 `<owner>-<repo>`；自然语言放 `summary` 和 `detail`。
- 外部轮询应先确认候选状态稳定，再发完成事件，避免把一次中间状态当成最终推送。
- 重试必须保留失败原因和尝试次数；调度方处理后要验证并关闭对应异常，而不是只隐藏卡片。
- 频限绕行属于待核实恢复事项：核实通过并回归原派发后才算关闭，不能只隐藏卡片。

## 控制台展示契约

| 区域 | 必须展示 |
| --- | --- |
| 正在运行 | 最近 5 条规则标题、所属项目、概要、状态和模型 |
| 等待重试 | 最近 5 条标题、所属项目、失败概要、尝试次数和模型 |
| 今日完成 | 最近 5 条标题、所属项目、概要、模型和计费信息 |
| 待调度处理 | 最近 5 条开放卡片、所属项目、失联或停止任务概要 |
| 调度规则 | 当前 Agent、实际发现的模型、权限、触发方式和工作目录 |
| 调度会话 | 当前本地 ACP 会话、状态、所属项目和关闭操作 |

频限绕行的会话在“等待重试”或“待调度处理”中显示“绕行中（原模型频限，核实恢复中）”及被拦模型/宿主；核实恢复回归后按正常条目展示。

调度会话展示规则：每个项目同时至多一个进行中的调度会话（服务端按项目查重）；项目进度相关视图每项目只取当前最新会话，不展示历史会话；异常退出的会话保留在列表中供诊断，直到被关闭或替换。

项目进度展示规则：同一项目存在多条串行链文件（`*-serial.json`）时，只显示最近更新的一条链（按链文件 `lastEventAt` 比较），旧链让位，不并排显示。

项目进度链行同时显示整条链的累计用量：自链相关规则（链文件词干前缀匹配）首次运行以来的累计输入/输出 Token 与计费，口径与计费优先级一致（已上报费用 → Token +「费用未上报」→「暂无用量」），只信 Hub 上报值，不按模型名称估算。

链/项目累计的取数口径（2026-11-18 定稿）：Hub 规则行 `totals.usage` 只是当日窗口（按天重置），不能当累计。真·累计由控制台服务端翻页读取 `/v1/state` 的 runs 历史（`?before=<id>` 向前翻，runs 只增不删），逐轮累加进运行目录 `chain-usage.json` 台账：

- 只计已开始且已终态的轮次（有 `finishedAt`，且 `claimedAt` 或 `usage` 存在），与中台 §6.2 spending 口径一致；从未开跑就取消的轮次不计入轮数。
- 费用缺失的轮次计入「未上报」计数，`cost` 保持 null，不用零冒充上报。
- 已见 run id 去重，重复读取、翻页重叠、并发路由共享扫描都不会重复计费。
- 单次刷新翻页预算用满时把断点写进台账，下一轮从断点续翻；没翻到底之前结果带「历史补全中」标记并在界面如实标注，绝不把部分覆盖冒充全量。
- 未完成轮次一律不阻塞扫描前沿：中台把全部 queued/claimed/unknown 轮次并入第一页，控制台对在册未完成轮次用 `?before=<id+1>` 做定向核实（每轮限额，超额顺延不丢账），因此它哪怕很久以后才完成、且完成时已掉出首页窗口，照样被补计，费用不丢。
- 在册数量有上限，超出部分记为「长期未完成未计入」轮数并在界面如实标注，不静默丢账。
- 扫描调度与结果缓存分离：只有真实扫描会推进下次扫描时刻，本地重建结果不续期调度，否则双路由（链进度与项目用量的签名不同）持续轮询会把台账冻结在首扫那一刻。
- 中台不可用或处于失败退避期时：已落盘台账按当前链集合与规则表本地重建，路由照常 200（不把项目进度面板打成 502）；进程内首次扫描就失败且没有任何台账时，界面显示「暂无用量 · 历史补全中」，不回到规则行今日窗口冒充累计。
- 稳态零写入：本轮没有任何新入账或游标推进时不重写台账文件，避免外置盘上的常态化写放大。
- 台账只写本模块（逐页 tmp+rename 原子落盘，收尾写入复用状态锁；状态锁被占用不算中台故障）。

项目累计同口径（`/api/project-usage`）。

任务概要必须展示该任务所属项目；项目优先使用任务上报的项目标识，其次使用调度规则工作目录。无法识别时如实显示“未识别”，不得编造。

计费优先级：已上报费用 → 输入/输出 Token + “费用未上报” → “费用未上报”。不得根据平台或模型名称伪造金额。

计费来源与口径（2026-11-16 主人确认）：费用与 Token 只来自各 Agent 插件自报，控制台不做任何折算或估算。Claude Code 按 Anthropic API 牌价上报 `total_cost_usd`（续跑会话取本轮增量，不重复计费）；Codex 只报 Token 不报费用；WorkBuddy 两者都不报。因此链累计美元是混合口径——订阅 coding plan 下 Claude 的金额为牌价等值而非实际扣款（实际消耗订阅额度，各平台 limit 控制台不可见），Codex/WorkBuddy 轮次不计入美元。该口径已获主人确认，不做"折算"/"按 Agent 拆分"等额外标注。

输入框抗打断的已知限制：持有焦点的会话卡片与答案卡片在后台刷新（每 2 秒）时整棵复用旧 DOM 节点，避免节点替换打断输入法组词；钉住期间该卡片内容暂停更新到失焦或提交为止，卡片上的状态徽标、流式输出与按钮可能过期（持续至失焦或提交）。对过期状态的操作由服务端（Hub）拒绝并提示，不造成数据损坏；请勿把钉住期间的停滞当作刷新故障上报。

## 当前实现与运行时能力的边界

当前公开仓库实现上述状态展示、规则管理和受限操作 API。原试点中的异常扫描、远端轮询、部署和平台包装脚本包含真实运行目录或目标项目配置，因此不作为通用实现直接公开。

这些运行时能力在本契约中保留为明确要求；后续入库必须先泛化配置、去除秘密和私有业务语义，并把现有行为测试一并迁移。文档存在不代表相应运行时脚本已经由本仓库提供。

频限绕行的通用运行时机制已由本仓库提供：`src/detour.mjs` 维护运行目录下的 `detours.json` 登记（被拦 Agent/模型、证据、替代方案、冷却节奏），`scripts/detour.mjs` 提供 record/verify/verify-all/revert/status；verify 执行登记时给定的探测命令，通过即把 rules.json 原子回归原派发（登记与回归各留带标识的 `.bak`，已离开替代 Agent 的规则不强拽）；登记、核实、回归与控制台规则表单保存共用状态锁互斥；登记写失败自动回滚 rules.json；改坏的 detours.json 留档隔离而不卡死核实。探测命令按 Agent 而异，由登记时显式给出，仓库不提供具体 Agent 的探测实现。自动侦测脚本 `scripts/quota-scan.mjs`、路由政策表 `src/detour-policy.mjs` 与 cron 模板见 §12。

## 12. 额度绕行机械化（自动侦测 / 政策路由 / 定时探针）

本节落实 AGENTS.md §4.12：额度耗尽才绕行，探针探到恢复自动切回，全系统通用而非单会话专用。
机制不升级用户、不计入重试纪律的失败次数，也不改变"恢复后原平台重新成为默认"的口径。

### 12.1 路由政策表（代码配置 + 文档）

主人定死的默认表（`src/detour-policy.mjs` 的 `DEFAULT_POLICY`）：

| 工作类型 | 主 Agent | 备选 Agent | 说明 |
| --- | --- | --- | --- |
| dev（开发） | workbuddy | claude | 额度耗尽才由 workbuddy 切 claude |
| review（审阅） | claude | codex-full | 独立审阅仍优先可靠性，不因省钱降档 |

- 可按项目覆盖：运行目录放 `detour-policy.json`（属本机运行状态，不入库），结构
  `{"defaults":{...},"projects":{"<项目 cwd>":{"dev":{"primary":"...","fallback":"..."},"review":{...}}}}`；
  以最长 cwd 前缀匹配的项目条目为准，逐类型覆盖全局默认。
- 只有在被拦 Agent 是该类型的**主** Agent 时才自动改派到备选；已经处于备选时 `resolveFallback` 返回空，
  不再自动往下绕，留给调度会话按第 9/10 条处理。判不出工作类型（如纯扫描规则）不自动登记。

### 12.2 自动侦测 `scripts/quota-scan.mjs`

两条独立扫描通道共用同一连续计数与裁定：
- **worker 轮次**：只读 `<AGENT_AUTOLOOP_HOME>/worker/runs/<轮次号>-<尝试号>/` 最近 `window` 个（默认 200），
  从 `stdout-*.log` / `stderr-1.log` 的 `error` 原文与退出码判定失败；Agent/模型取自 `entry.json` 的
  `job.agent.id` / `model`，缺失时按命令里的 `--model` 等特征推断；工作类型按规则名（开发/dev、审阅/review）判定。
- **Hub 调度回合**（2026-11-19 主人定）：只读 `<AGENT_AUTOLOOP_HOME>/hub.db` 的 `runs` 视图（用系统 `sqlite3 -json`），
  `error` 或 `summary` 命中额度模式的 run（含仍在 `queued`/`claimed` 排队重试的）也算失败轮次；
  `done`/`nothing` 打断连续命中。工作类型按规则名（coord/调度会话、dev、review）判定；命中后按政策表绕行到**同一档**的备选平台执行者。
- 额度拒绝模式可配：默认 `429, refusal, 配额, quota, 额度, rate.?limit, exhausted, too many requests`，
  `--patterns` 整体替换。编译失败、网络错误等**非额度失败不触发**，并打断同一 agent+model 的连续命中。
- 同一 agent+model 连续 3 次额度命中（`--threshold` 可配）才自动登记：调 `recordDetour`，
  经 `withStateLock` 原子改派备选、失败回滚 `rules.json`，写穿 `detours.json` 留 `.bak`；
  控制台 `/api/detours` 可见（展示经 `publicDetour` 剥掉探测命令）。已有同 agent+model 在途绕行则幂等跳过。
- §12 必填字段全部由证据自动写入：`origin: auto-scan`、被拦 agent/model、`blockedAt` 时间、
  `evidence`（命中模式 + 各轮 `run <id>「证据原文」` + 最近命中时间）、被改派规则及原派发。
- 探测命令按 Agent 而异：显式 `--probe` 优先；未传时按 `scripts/detour-probe.mjs` 的
  `probeCommand(agent)` 自动拼接——`acp`（去掉 `--acp` 追加 `-p <ping>`）、`claude`/`codex`（追加 `-p`/`exec` ping 与 `--model`）。
  拼不出（无 command/program 或未知 use）时登记仍成功但不带探测命令，定时核实时该项会跳过并要求人工回归。
- `--dry-run` 只报候选不写文件；`--json` 输出机器可读摘要。

cron 规则模板 JSON（`to` 用 `command` 类无模型执行者，prompt 只汇报，不自行改规则）。
**启用前必须先在 `agents` 里登记同名执行者**（如
`"quota-scan":{"use":"command","command":["sh","-c","AGENT_AUTOLOOP_HOME=<root> node <repo>/scripts/quota-scan.mjs --json"],"access":"read"}`，
`"detour-verify":{...verify-all...}`），否则 rules.json 保存校验会因 `to` 未注册而失败。

```json
{
  "name": "额度拒绝自动侦测",
  "when": { "cron": "*/15 * * * *" },
  "to": "quota-scan",
  "cwd": "<AGENT_AUTOLOOP_HOME>",
  "prompt": "无模型扫描：连续额度拒绝自动按政策绕行，只汇报；除该脚本外不改 rules.json、不改 detours.json、不手工 revert。非额度失败不要登记。",
  "resume": false
}
```

### 12.3 自动回归（定时探针 + 退出码）

- `node scripts/detour.mjs verify-all [--json] [--timeout 120000]` 批量核实**所有**到期登记：
  对每条执行其探测命令；探到恢复即 `markProbeResult(ok)` 原子回归原 Agent（跳过已离开备选的规则），
  记录 `probe-ok`/`reverted` 并写穿 `detours.json`；未恢复的继续绕行，等待下一冷却窗口。
  这是全系统通用行为：任一会话、任一 cron 轮次探到恢复都会切回，不依赖原会话是否还在。
- 退出码约定（cron 据此判断是否告警）：`0`=核实完成或无到期项；`1`=至少一条探测未通过或处理出错；
  `2`=用法或配置错误（如 `--timeout` 非法）。`--json` 输出 `{due,ok,failed,errors,skipped,results,notes,exitCode}`。
  没有探测命令的登记计为跳过而非失败（提示用 `revert` 人工回归），不把跳过伪装成"已通过恢复"。
- 旧 `verify` 保持兼容语义：只有处理出错才退出 1，探测未通过仍退出 0；cron 一律用 `verify-all`。

cron 规则模板（每 30 分钟，提示词只调用 verify 并汇报，不手工改规则）：

```json
{
  "name": "绕行定时核实",
  "when": { "cron": "*/30 * * * *" },
  "to": "detour-verify",
  "cwd": "<AGENT_AUTOLOOP_HOME>",
  "prompt": "无模型核实：只运行 detour.mjs verify-all，按退出码汇报（0=全部核实完成，1=仍有未恢复，2=配置错误）；不要手工改 rules.json 或 detours.json，也不要跳过探测直接 revert。",
  "resume": false
}
```

对应的系统 cron 模板（与上面的规则模板二选一；`<REPO>`、`<AGENT_AUTOLOOP_HOME>` 为部署时替换的占位符）：

```cron
*/15 * * * * cd <REPO> && AGENT_AUTOLOOP_HOME=<AGENT_AUTOLOOP_HOME> node scripts/quota-scan.mjs --json >> <AGENT_AUTOLOOP_HOME>/logs/quota-scan.log 2>&1
*/30 * * * * cd <REPO> && AGENT_AUTOLOOP_HOME=<AGENT_AUTOLOOP_HOME> node scripts/detour.mjs verify-all --json >> <AGENT_AUTOLOOP_HOME>/logs/detour-verify.log 2>&1
```

### 12.4 边界

- 自动侦测与核实只在运行目录内读写 `rules.json` / `detours.json`，复用与控制台表单保存、人工登记同一把状态锁；
  不把真实项目配置、凭据或路径写进本仓库，模板中一律用占位符。
- 绕行登记与回归都有留痕和备份；恢复后按政策表回到主 Agent，不把备选沉淀为新的默认偏好。

## 13. DAG 节点卡住发现（无模型，2026-11-19）

### 13.1 状态变化即唤醒（2026-11-19）

卡住只能发现"出错了没人管"，发现不了"正常推进但没人接下一轮"。
控制器每一轮 tick 记录本轮各节点状态变化（`dev / review / accepted / blocked / gated`），
合并成一条 `scheduling.message`（subject=`scheduling:dag:<runId>`）投给调度会话；
瞬时错误（中台超时等）仍归卡住巡检，不在此处叫醒。

- **合并**：一轮内所有节点的变化合一条，不逐条发；同链复用同一事项。
- **去重**：事件 ID `console:dag-progress:<runId>:<sha1(progress)[:12]>`——同一批变化重投幂等，换一批变化即新事件；进程内按 ID 去重，中台对重复 ID 不重复执行兜底。
- **失败不阻断**：投递失败只记日志，不影响本轮推进与持久化。
- **出口**：仍是中台原生 `POST /v1/events`（来源密钥），不加新规则、不改协议字段。
- 调度会话收到的 `detail` 除 `project,text` 外还带 `progress` 明细，便于直接接手下一轮动作。

背景：DAG 控制器把节点推进错误只写在 `dag-runs/*.json` 的 `publish.nodes.<id>.lastError`，每轮重试时覆盖；
中台异常扫描只看卡片与 run，看不到这里。2026-11-19 device-binding 推送因凭据缺失连续失败，链停摆而无人发现。

- **记账（`src/dag-controller.mjs`）**：每轮末与上一轮比较节点错误——同一错误保留 `errorSince`（首次时间）并累计 `errorCount`；换了错误重新计时；无错误清掉两个字段。不改推进逻辑。
- **发现（`src/dag-stall.mjs`，控制台进程内每 5 分钟）**：非终态 DAG 中同一错误持续 ≥10 分钟的节点即为卡住；
  经中台原生 `POST /v1/events`（来源密钥）投 `scheduling.message`，`subject=scheduling:dag-stall:<runId>`，
  `detail={project,text}`，由现有「调度会话执行」规则接住，同一条链复用同一事项会话。
- **去重**：事件 ID `console:dag-stall:<runId>:<nodeId>:<errorSince>`，中台对重复 ID 不重复执行，同一次卡住最多唤醒一次；进程内另记已投递 ID 免重复请求。投递失败下轮重试。
- **处理**：唤醒文本要求调度方定位根因、工程问题自行修复或派 worker、修好后由控制器自动重试；只有用户掌握的凭据/授权才提问；文本以「核实后本轮结束」收尾，防止单轮空转。
- **安全**：错误原文进中台前抹掉 URL 凭据与 GitHub token，截断至 600 字符。
- **开关**：`AUTOLOOP_DAG_STALL=0`（或 `AUTOLOOP_DAG=0`）关闭。不新增中台规则、不改协议字段。

## 验收示例

1. **部署失败但代码已推送**：开发调度仍继续；部署卡片独立处理，不阻塞开发。
2. **连续重试**：无模型扫描发现异常并冷却去重，调度 Agent 读取原因、修复、验证和恢复。
3. **缺少 NAS 凭据**：调度方不自行扩权，向用户说明缺失项和恢复路径。
4. **WorkBuddy 只有 Token 无费用**：今日完成显示 Token 与“费用未上报”，不显示估算美元金额。
5. **目标任务并行开发**：每个 worker 使用自己的目标项目 worktree，控制面仓库不出现目标业务文件。
6. **无 HOME 的公开环境**：模型标签显示默认文案，不读取任何固定个人账户目录。
